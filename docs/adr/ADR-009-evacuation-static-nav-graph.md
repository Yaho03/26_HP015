# ADR-009: 탈출 경로는 사전 정의된 정적 네비게이션 그래프 위에서 계산한다

| 항목 | 내용 |
|------|------|
| 상태 | Proposed |
| 결정일 | 2026-08-21 |
| 결정자 | — (검토 필요) |
| 관련 | FR-801~808, `12_EVACUATION_ROUTE_SPEC.md`, ADR-005 |

## 배경

위험 상황에서 작업자에게 탈출 경로를 제시하려면 "어디를 지나갈 수 있는가"를 시스템이 알아야 한다. 그런데 현재 저장소에는 **공간의 통행 가능 구조를 기술한 데이터가 전혀 없다**. 있는 것은 센서 노드 4개의 고정 좌표와 공간 치수(60 × 20 × 14m)뿐이다.

밀폐공간은 빈 상자가 아니다. 비계(scaffold)가 세워져 있고, 사다리로 층을 오르내리고, 출입구(manhole)는 한두 개뿐이며 대개 좁다. 격자(grid) 기반 경로 탐색은 이런 구조를 표현하지 못한다 — 사다리는 격자 위에서 그냥 벽이다.

## 결정

통행 가능 구조를 **노드-엣지 그래프**로 사전에 정의하고, 경로는 이 그래프 위에서 Dijkstra로 계산한다.

```
nav_nodes  : 통행 가능 지점 (바닥 지점, 비계 데크, 사다리 상·하단, 출구)
nav_edges  : 지점 간 이동 가능 여부 + 이동 종류(walk / scaffold_plank / ladder)
exits      : 최종 목적지 (manhole / hatch)
```

엣지 비용은 **정적 비용 × 동적 위험 가중치**다.

```
edge_cost = length_m × traverse_factor(kind) × hazard_multiplier(edge, active_hazards)
```

`traverse_factor`는 이동 종류별 상수(walk 1.0 / scaffold_plank 1.3 / ladder 2.5)이고, `hazard_multiplier`는 활성 HazardZone과의 교차 여부로 매 계산마다 갱신된다. **그래프 구조는 정적, 비용은 동적**이다.

작업자의 현재 위치는 그래프 위의 점이 아니므로, 가장 가까운 `nav_node`에 스냅해 시작점으로 삼는다(`entry_nav_node_id`, `snap_distance_m`).

## 대안

| 대안 | 결과 | 이유 |
|------|------|------|
| 정적 nav graph + Dijkstra | 채택 | 사다리·비계를 자연스럽게 표현. 노드 수십 개 규모라 계산이 즉시 끝남. 그래프 자체가 검토 가능한 산출물 |
| 균일 격자 + A* | 기각 | 사다리·수직 이동 표현 불가. 밀폐공간 형상에서 격자 해상도만 낭비됨 |
| 내비메시(NavMesh) 자동 생성 | 기각 | 3D 모델에서 자동 추출하려면 별도 툴체인 필요. MVP 범위 초과 |
| 최단 직선 + 장애물 회피 없음 | 기각 | 비계를 통과하는 경로가 나온다. 안전 기능으로서 무의미 |

## 결과

**긍정:**
- 비계·사다리 구조가 데이터로 명시되어, 현장이 바뀌면 그래프만 갱신하면 된다
- 위험 가중치를 엣지에 얹는 구조라 "가스가 찬 통로를 우회"가 자연스럽게 나온다
- 그래프가 작아(수십 노드) 재계산 지연이 무시할 수준이다

**부정:**
- **그래프를 사람이 만들어야 한다.** 현장 실측 → YAML 작성이 선행 작업이며, 이 데이터가 틀리면 경로도 틀린다. 이건 소프트웨어로 검증할 수 없다
- UWB 측위가 2D(z=0 고정)이므로 **작업자가 비계 몇 층에 있는지 알 수 없다.** MVP는 항상 최하층(`assumed_level_id: "L0"`)에 있다고 가정하고, 화면에 이 가정을 명시한다
- 그래프에 없는 경로(임시 통로, 비상 개구부)는 시스템이 모른다. 경로는 **참고 정보이며 현장 판단을 대체하지 않는다**는 면책이 필수다
