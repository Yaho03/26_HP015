# ADR-010: 탈출 경로는 백엔드가 ship-visual 균일 배율로 계산한다

| 항목 | 내용 |
|------|------|
| 상태 | Proposed |
| 결정일 | 2026-08-21 |
| 결정자 | — (검토 필요) |
| 관련 | ADR-009, FR-801~806, `12_EVACUATION_ROUTE_SPEC.md` §2.4, `05_DIGITAL_TWIN_SPEC.md` §3.1.1/§3.1.4 |

## 배경

`05_DIGITAL_TWIN_SPEC.md` §3.1.1은 명확한 규칙을 세워두었다.

> 실시간 location WebSocket 프레임은 `position_raw` 와 `source_coordinate_system` 만 보낸다. 표시 좌표는 보내지 않는다 — 화면마다 매핑 프리셋이 다르므로 백엔드가 어느 하나를 고를 수 없다. 변환은 프론트엔드가 렌더 시점에 한다.

탈출 경로는 이 규칙과 충돌한다. 세 가지가 겹친다.

1. **nav graph는 실제 선박 치수여야 한다.** 축소 데모 공간(2.5 × 2.0m)에 비계와 사다리를 배치하는 것은 물리적으로 성립하지 않고, 이동 거리·시간이 실제 작업을 대표하지 못한다.
2. **UWB 실측 좌표는 `demo-local`(2.5 × 2.0m)이다.** 그래프와 좌표계가 다르므로 어딘가에서 변환이 일어나야 한다.
3. **프리셋이 두 개인데 하나는 쓸 수 없다.** §3.1.4의 `FILL`은 x를 24배, y를 6.5배로 확대하는 **비균일** 매핑이다. 비균일 좌표에서는 거리가 방향에 따라 다르게 계산되므로, Dijkstra가 고르는 "가장 가까운 출구"가 실제와 다른 출구가 된다.

## 결정

경로 계산에 필요한 좌표 변환을 **백엔드가 수행한다.** §3.1.1 규칙의 의도적 예외다.

| 항목 | 결정 |
|------|------|
| nav graph 좌표계 | `ship-visual` (60m × 20m × 14m) |
| 매핑 프리셋 | **`TRUE SCALE` 균일 6.5배 고정.** `FILL` 사용 금지 |
| 변환식 | 새로 만들지 않는다. `05_DIGITAL_TWIN_SPEC.md` §3.1.1 식을 그대로 사용 |
| 경로 메시지 `coordinate_system` | `ship-visual` |
| 프론트엔드 추가 변환 | 없음. Z-up → Y-up 축 변환(§3.2)만 적용 |
| `FILL` 화면(모니터링 축소 트윈) | **경로를 표시하지 않는다** |

예외를 인정하는 근거는 **경로가 표시물이 아니라 기하 계산 결과**라는 점이다. §3.1.1이 백엔드의 좌표 변환을 금지한 이유는 "화면마다 프리셋이 다르므로 백엔드가 고를 수 없다"는 것인데, 경로는 화면 사정과 무관하게 **거리가 보존되는 좌표계 하나에서만 성립한다.** 고를 수 없는 문제가 아니라 고를 것이 하나뿐인 문제다.

계산을 프론트로 내리는 대안은 더 나쁘다. `no_safe_route` 판정이 level3 경보를 발령하는데, 판정이 프론트에 있으면 **백엔드의 경보와 화면의 경로가 서로 다른 그래프에서 나온다.** 안전 판정은 백엔드에 있어야 한다.

## 대안

| 대안 | 결과 | 이유 |
|------|------|------|
| 백엔드가 `TRUE SCALE`로 변환 후 계산 | 채택 | 거리 보존. 안전 판정이 백엔드에 유지됨 |
| nav graph를 `demo-local`(2.5 × 2.0m)로 작성 | 기각 | 2.5m 공간에 비계·사다리가 성립하지 않는다. 거리·시간이 무의미해진다 |
| 프론트엔드에서 경로 계산 | 기각 | `no_safe_route` 경보와 화면 경로가 다른 그래프에서 나온다 |
| 백엔드가 `FILL`로 변환 후 계산 | 기각 | 비균일 배율이라 "가장 가까운 출구"가 틀려진다 |
| 주입 시나리오만 `ship-visual`로 발행 | 부분 채택 | 시연에는 충분하고 §3.1.1에 이미 규칙이 있다. 다만 실물 UWB 연동 시 변환이 필요하므로 이 결정을 대체하지 못한다 |

## 결과

**긍정:**
- 경로 거리·예상 시간이 실제 선박 치수 기준으로 의미를 갖는다
- 안전 판정(`no_safe_route` → level3 경보)이 백엔드에 유지된다
- 변환식을 새로 만들지 않아 좌표계가 두 벌이 되지 않는다
- 주입 시나리오를 `ship-visual`로 발행하면 변환이 이중으로 걸리지 않는다 (§3.1.1 기존 규칙)

**부정:**
- §3.1.1 규칙에 예외가 생긴다. 이후 좌표 관련 작업자가 "백엔드는 변환하지 않는다"를 무조건 참으로 읽으면 안 된다
- 모니터링 화면(`FILL`)에서 경로를 볼 수 없다. 경로를 보려면 3D 트윈이나 2D 평면도로 이동해야 한다
- **축소 공간을 6.5배로 확대하므로 UWB 위치 오차도 6.5배로 확대된다.** 데모 공간에서 5cm 오차는 확대 후 32.5cm가 된다. 경로 시작점 스냅이 그만큼 부정확해지며, 실물 UWB 검증 후 재평가가 필요하다
