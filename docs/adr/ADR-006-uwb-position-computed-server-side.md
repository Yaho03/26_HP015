# ADR-006: UWB 좌표 계산 위치 — 백엔드

| 항목 | 내용 |
|------|------|
| 상태 | Accepted |
| 결정일 | 2026-08-16 |
| 결정자 | 팀 합의 |
| 관련 | 이슈 #121, ADR-002(DS-TWR), #69(least_squares_2d) |

## 배경

`least_squares_2d()` 는 `backend/app/services/uwb_positioning.py` 에 구현되어 있고
단위 테스트도 있으나, **호출부가 `experiments/` 뿐이었다.** 프로덕션 경로는
`wearable/{id}/location` 으로 들어온 `x_m`/`y_m`/`z_m` 을 그대로 신뢰했다.

즉 태그가 좌표를 계산해 보낸다고 암묵적으로 가정한 상태였고, 이 가정이 문서에
없었다. 누가 삼변측량을 하는지 정하지 않으면 펌웨어와 백엔드가 서로 상대가 할
것이라 생각하고 아무도 안 하게 된다.

## 결정

**노드가 앵커까지의 거리를 발행하고, 백엔드가 삼변측량한다.**

새 토픽 `wearable/{node_id}/ranging` 을 추가하고, 백엔드가 앵커 좌표를 설정으로
알고 있다가 `least_squares_2d()` 로 좌표를 계산한다. 계산 결과는 기존 위치
경로(`LocationFilter` → WebSocket)에 그대로 흘린다.

기존 `wearable/{node_id}/location` 경로는 **유지한다.** 자체 측위를 하는 상용
태그를 붙일 여지를 남긴다. 두 경로 모두 같은 필터와 브로드캐스트를 거친다.

## 대안

| 대안 | 결과 | 이유 |
|------|------|------|
| (b) 노드가 거리 발행, 백엔드 계산 | **채택** | 앵커 배치 변경 시 펌웨어 재작성 불필요. 계산 근거(앵커 수·거리)가 서버에 남아 디버깅 가능. 펌웨어 부담 감소 |
| (a) 태그가 계산 후 좌표 발행 | 기각 | 앵커 좌표가 펌웨어에 박힘. 배치를 바꿀 때마다 전 태그를 다시 구워야 함. 측위 실패 원인을 서버에서 알 수 없음 |

## 근거 보강

**앵커 좌표는 설치 정보지 텔레메트리가 아니다.** 페이로드에 앵커 좌표를 싣는
방안도 검토했으나, 같은 값을 매 5Hz 메시지마다 반복해 보내는 낭비이고, 태그마다
다른 값을 보내면 정합성이 깨진다. 서버 설정(`UWB_ANCHORS`)이 단일 정본이다.

## 결과

**긍정**
- 하드웨어 없이도 목업 거리 주입(`worker_walk_uwb`)으로 프로덕션 측위 경로를
  그대로 검증할 수 있다.
- 앵커 가림·반사로 측위가 실패하면 서버가 인지하고 좌표를 내보내지 않는다.
  추측한 좌표로 작업자를 엉뚱한 곳에 표시하지 않는다.

**부정**
- 백엔드가 앵커 배치를 알아야 한다. 현장에서 앵커를 옮기면 `UWB_ANCHORS` 설정을
  갱신해야 하며, 잊으면 위치 전체가 틀어진다. 파싱 실패 시 부팅에서 크게
  실패하도록 해 조용한 오류를 막았다.
- 거리 → 좌표 계산이 서버 부하로 옮겨온다. 태그 1대 5Hz 기준 무시할 수준이나,
  다중 태그로 확장하면 재검토가 필요하다.

## 구현

| 항목 | 위치 |
|------|------|
| 삼변측량 | `backend/app/services/uwb_positioning.py` (`least_squares_2d`) |
| 수신·변환 | `backend/app/services/uwb_service.py` |
| 앵커 설정 | `settings.uwb_anchors` — `"A1:0,0;A2:2.5,0;A3:2.5,2.0;A4:0,2.0"` |
| 토픽 | `wearable/{node_id}/ranging` (04_DATA_CONTRACT 4.6) |
| 목업 주입 | `experiments/inject` 시나리오 `worker_walk_uwb` |
