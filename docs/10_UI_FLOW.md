## 3. Screen 1: 실시간 모니터링

> 관련 요구사항: FR-401

### 3.1 레이아웃 — 5분할 관제 콘솔

기준 해상도 **1440 × 900 (데스크톱 관제 모니터)**. **세로 스크롤이 발생하면 안 된다.**
관제 화면은 원거리에서 훑는 용도라, 스크롤이 생기는 순간 화면 밖의 값은 없는 값이 된다.
각 칸은 자기 안에서 스크롤을 받고 페이지 자체는 늘어나지 않는다.

```
┌──────────────────────────────────────────┬─────────────────────┐
│                                          │  ② 위험 센서 상세    │
│  ① 디지털 트윈 히트맵                      │     (동적 높이)      │
│     (사선 탑뷰 크롭)                       ├─────────────────────┤
│                                          │  ③ 센서 4종 + 웨어러블 │
├──────────────────────────────────────────┤     요약 (동적 높이)  │
│  ⑤ 노드별 센서 데이터 (2×2)                ├─────────────────────┤
│     + 웨어러블 상태 스트립                  │  ④ 최근 위험 로그     │
└──────────────────────────────────────────┴─────────────────────┘
```

| 영역 | 비율 |
|------|------|
| 좌측 컬럼 / 우측 컬럼 | 68% / 32% |
| 좌측 세로: ① / ⑤ | 46% / 54% |
| 우측 세로: ② / ③ | 동적 (§3.5) |
| 우측 세로: ④ | 고정 180px |

TopBar와 SideNav는 그대로다. 재설계 범위는 `MonitoringScreen` 내부다.

**반응형** — §12의 브레이크포인트를 따른다. 1280px 미만에서는 우측 컬럼이 좌측 아래로
내려가는 1열 스택이 되고, **그때만** 세로 스크롤을 허용한다. 스택 모드에서는 칸이 내용
만큼 늘어난다 — 페이지가 스크롤되는데 칸마다 내부 스크롤까지 만들면 스크롤 컨테이너가
이중으로 겹쳐 조작이 엉킨다. ④ 만 예외로 220px 고정이다.

### 3.2 ① 디지털 트윈 히트맵

3D 디지털 트윈을 **사선 탑뷰로 크롭**해, 화물창 바닥의 가스 분포·센서 위치·작업자 위치를
한 화면에서 읽게 한다. 별도의 2D 평면도를 그리지 않는다 — 평면도와 트윈이 따로 있으면
두 그림의 노드 위치가 어긋나는 순간 어느 쪽이 맞는지 알 수 없게 된다.

| 항목 | 구현 |
|------|------|
| 컴포넌트 | `components/TwinScene.tsx` 재사용 (`mode="plan"`) |
| 카메라 | 타깃 = 바닥 중앙, 위치 = `[30, fit*0.82, -fit*0.58]` (수평 대비 ≈ 55°) |
| 절개 | `cutaway = mode !== "inside"` — 카메라 쪽 측벽을 잘라 바닥을 보인다 |
| 시점 조작 | **비활성** (`interactive={false}`) — 시점이 돌아가면 ⑤ 격자와의 대응이 깨진다 |
| 모드 토글 | 표시하지 않는다 (Screen 2 소관) |
| 히트맵 | `components/Heatmap.tsx` + `utils/idw.ts` |

**표시 의무 (PRD FR-402 MUST)** — 칸 하단에 항상 표시한다.

- `Estimated concentration based on IDW interpolation`
- `Interpolation based on N sensors` (N = 온라인 노드 수)
- 좌표 배지: `LIVE` / `SIM` / `대기` + `demo-local → ship-visual`
- 온라인 노드가 3개 미만이면 `Insufficient data for interpolation` 오버레이(§4.6)를 덮고
  히트맵을 아예 그리지 않는다. 보간 못 하는 상태를 빈 화면으로 두면 "가스가 없다"로 읽힌다.

**이번 범위 아님** — 위험 상황 시 작업자 탈출 경로 표시는 후속 기능이다. `TwinScene` 에
`escapeRoute?: { path: Position3D[]; exit_id: string } | null` 을 선택적 prop 으로만
선언해 두고, 값이 들어와도 아무것도 렌더하지 않는다. 경로 계산 로직(그래프 탐색, 가스
코스트 함수)은 작성하지 않는다.

### 3.2.1 ③ 센서 요약 카드

정상 상태에서 화면 대부분을 쓰는 칸이다. 주의 이상 노드가 생기면 그 노드를 ② 로
넘겨주며 줄어들기 때문에, **카드 높이를 짧게 유지하는 것**이 이 칸의 제약이다.

**칸 헤더** — `공간 O₂ 20.9%`. O₂ 센서는 웨어러블에만 있고 센서 노드에는 없으므로
카드마다 반복하지 않고 헤더에 한 번만 표시한다. 등급은 `classifyO2Low` / `classifyO2High`
로 판정하고 §8.5 대로 `센서 응답 지연 가능성 (최대 15초)` 라벨을 함께 단다.

**카드 1장 구성** — 이 시스템의 질식 유발 가스는 CO₂(단순질식+독성), CO·H₂S(화학적 질식),
O₂ 결핍 4종이다. 온도·습도·가스저항은 질식과 무관하므로 정상일 때 카드에 띄우지 않는다.

```
┌──────────────────────────────┐
│ ✓ S1   정상          LIVE     │  ← 아이콘 + 텍스트 라벨 + 데이터 출처
│ 612 ppm       ▁▂▁▃▂▁         │  ← 유일하게 교정된 값이므로 큰 수치 + 스파크라인
│ CO [정상] ▇▁▁   H₂S [UNCAL]  │  ← 수치 없이 상태 칩 + 임계 근접 바
│ ↗ 추세 유지 시 약 12분 뒤 L1   │  ← 선제 표시 (06_ALERT_RULES §8.2)
│ ▸ 6종 전체                    │  ← 클릭 시 펼침
└──────────────────────────────┘
```

- **CO₂만 큰 수치.** CO·H₂S는 수치를 띄우지 않고 상태 칩과 임계 근접 바만 보인다.
  미교정 MQ 센서가 보내는 값은 ppm 이 아니라 Rs/R0 저항비다. 이것을 ppm 처럼 크게
  띄우면 오독을 부른다. 실제 값이 필요하면 카드를 펼치거나 ⑤ 표를 본다.
- 상태 칩: `정상` / `주의` / `경고` / `위험` / `UNCAL` / `WARM` / `ERR` / `N/A`
- 6종 전체는 **클릭 시 펼침**(`<details>`)으로 접근한다. 호버 펼침은 쓰지 않는다 —
  관제 화면에서 마우스가 스쳐 지날 때마다 카드가 튀어 오히려 스캔을 방해한다.

### 3.2.2 카드 등급 표현

**카드 등급 표현:**

배경색은 등급과 무관하게 패널색으로 고정한다. 등급은 **테두리 · 브래킷 마크 · CO₂ 수치
색상 · 상태 아이콘 · 텍스트 라벨**이 함께 전달한다. **위험도를 색상 단독으로 전달하지
않는다** — 색각 이상 사용자와, 화면을 비스듬히 보거나 조명이 반사되는 현장 모니터에서
색만으로는 등급이 전달되지 않는다.

| alert_level | 테두리 / 브래킷 | CO₂ 수치 | 아이콘 + 텍스트 |
|-------------|-----------------|----------|-----------------|
| normal | `--normal` | 기본 잉크색 | 체크 + `정상` |
| level1_caution | `--l1` | `--l1` | 삼각 경고 + `L1 주의` |
| level2_warning | `--l2` | `--l2` | 원형 경고 + `L2 경고` |
| level3_critical | `--l3` | `--l3` | 원형 오류 + `L3 위험` |

색상 토큰 값은 `frontend/src/styles/global.css`의 `:root` / `:root[data-theme="light"]`에
정의한다. 다크가 기본이며 라이트(주간) 모드는 같은 구조에 밝은 지면을 쓴다. 지켜야 할
것은 색값이 아니라 **정상 → 주의 → 경고 → 위험 순으로 위험도가 올라가는 의미 체계**다.

**교정 상태 배지:**

| calibration_status | 배지 | 표시 |
|--------------------|------|------|
| calibrated | 없음 | 정상 |
| uncalibrated | "UNCAL" | 회색 배지 |
| calibrating | "CALIBRATING" | 파란색 배지 (회전 아이콘) |

**센서 오류 배지:**

| quality.sensors 값 | 배지 | 색상 |
|---------------------|------|------|
| valid | 없음 | — |
| warming_up | "WARM" | 주황 |
| error | "ERR" | 빨강 |
| not_connected | "N/A" | 회색 |

### 3.3 웨어러블 상태 스트립 (⑤ 하단)

웨어러블은 고정 계측점이 아니라 **사람**이라 센서 표와 축이 다르다 (O₂·심박·낙상 vs
CO₂·CO·H₂S). 2×2 안에 5번째 칸으로 끼워넣지 않고 ⑤ 하단에 가로 1줄 전용 스트립으로 둔다.
같은 격자에 넣으면 센서 노드와 같은 종류로 읽혀서 비교 대상이 아닌 값끼리 비교하게 된다.

```
[홍길동 · 사번 A-1023]  O₂ 20.9%  ·  심박 82  ·  낙상 정상  ·  배터리 78%  ·  위치품질 GOOD (4 anchor)
```

| 요소 | 데이터 | Zustand 바인딩 |
|------|--------|---------------|
| 착용자 이름·사번 | `workerFor("wearable-01")` | `hooks/useAssignments.ts` |
| O2 농도 | `o2_pct` | `wearable.o2_pct` |
| 심박 | `heart_rate` | `wearable.heart_rate` |
| 배터리 | `battery_pct` | `wearable.battery_pct` |
| 낙상 상태 | `fall_detected` | `wearable.fall_detected` |
| 위치 품질 | `quality_score`, `anchor_count` | `wearable.location_quality` |

**위치 품질 표시:**

| quality_score | 표시 |
|---------------|------|
| >= 0.8 | "GOOD" (녹색) |
| 0.5 ~ 0.8 | "FAIR" (노랑) |
| < 0.5 | "POOR" (빨강) |
| 없음 (UWB 미연동) | "대기" (회색) |

> 낙상 감지 또는 O₂ 이상 시 이 줄 전체가 해당 등급색 테두리로 승격되고
> `FALL DETECTED` 오버레이가 붙는다.
>
> 착용자가 미배정이면 회색 `미배정` 으로 표시한다. 밀폐공간에서 "누가 안에 있는지"
> 모르는 것은 비어 있는 상태가 아니라 그 자체가 위험 정보다 (이슈 #136).

### 3.4 ② 위험 센서 상세

**헤더** — `SummaryBar`. 정상 / 주의 / 경고 / 위험 노드 수.

| 항목 | 계산 | 표시 |
|------|------|------|
| 정상 노드 수 | `alert_level == "normal"`인 온라인 노드 수 | 녹색 숫자 |
| 주의 노드 수 | `alert_level == "level1_caution"` | 노랑 숫자 |
| 경고 노드 수 | `alert_level == "level2_warning"` | 주황 숫자 |
| 위험 노드 수 | `alert_level == "level3_critical"` | 빨강 숫자 |
| 판정 불가 노드 수 | `alert_level == "unknown"` | 회색 숫자, 0 이면 칸을 만들지 않음 |

**본문** — 주의 이상 노드마다 확대 카드 하나. 카드에는 **6종 센서값 전부**를 표시한다.

| 지표 | 필드 | 비고 |
|------|------|------|
| CO₂ | `co2_ppm` | ppm |
| CO | `co_ppm` | 미교정 시 Rs/R0 + `UNCAL` 배지 |
| H₂S | `h2s_ppm` | 미교정 시 Rs/R0 + `UNCAL` 배지 |
| 온도 | `temperature_c` | ℃ |
| 습도 | `humidity_pct` | % |
| 가스저항 | `gas_resistance_ohm` | kΩ 로 환산 표시 |

각 값 옆에 **임계값 대비 근접도 바**와 **최근 5분 스파크라인**을 붙인다. 등급을 끌어올린
지표는 그 행이 강조된다(왼쪽 `▸` 마커 + 굵은 수치 + 배경 워시 — 색 단독이 아니다).
미교정 값은 ppm 이 아니므로 등급 상승 근거로 쓰지 않는다.

카드 하단: 경보 발생 시각, 활성 경보 목록, 배정 작업자. 활성 서버 경보가 없으면
`활성 서버 경보 없음 — 측정값 기준 등급` 으로 밝힌다. 조용히 비우면 "경보가 해제됐다"로
읽힌다.

n이 3~4로 커지면 카드가 세로로 다 안 들어가므로 ②는 내부 스크롤 컨테이너이고
**위험도 높은 순(L3 → L2 → L1)** 으로 정렬한다. 잘리는 쪽이 항상 덜 위험한 카드여야 한다.

### 3.5 ② ↔ ③ 연동 규칙

두 칸은 **하나의 세로 공간을 나눠 쓰는 한 쌍**이다. `주의(level1_caution) 이상` 인
온라인 노드 수를 `n` 이라 할 때:

| n | ② 높이 | ③ 높이 |
|---:|---:|---:|
| 0 | 15% | 85% |
| 1 | 35% | 65% |
| 2 | 52% | 48% |
| 3 | 68% | 32% |
| 4 | 82% | 18% |

- CSS 커스텀 프로퍼티(`--panel2-share` / `--panel3-share`)로 `grid-template-rows` 의
  `fr` 값을 제어하고 `transition: 260ms ease` 를 건다.
- **승격된 노드는 ③에서 빠지고 ②로 이동한다.** 두 칸에 중복 표시하지 않는다.
  이것이 ③이 줄어드는 이유다 — 겹치면 비율만 바뀌고 내용은 그대로가 된다.
- 승격 조건은 세 가지를 모두 만족해야 한다: ①노드 데이터가 있을 것 ②온라인일 것
  ③등급이 주의 이상일 것. 오프라인 노드의 멈춘 값으로 위험 상세를 채우지 않는다.
- `unknown`(임계값 미수신으로 판정 불가)은 승격 대상이 **아니다.** `normal` 로도
  취급하지 않는다 — ③에 회색 상태로 남긴다 (이슈 #165, `utils/alerts.ts`).

> 구현: `frontend/src/utils/consoleSplit.ts` 가 이 규칙의 단일 소스이고,
> `consoleSplit.test.ts` 가 높이 표·승격 조건·중복 금지·정렬 순서를 붙잡는다.

### 3.6 ⑤ 노드별 센서 데이터 (2×2)

이 칸이 맡는 고유한 일은 **노드 간 비교와 추세 판독**이다. ③(현재값 글랜스)이나
Screen 3(시계열 차트)과 역할이 겹치면 안 된다.

**한 칸 = 한 센서 노드.** 각 칸 내부는 지표별 행으로 된 표다.

| 지표 | 현재값 | 임계값 대비 바 | 최근 5분 스파크라인 |
|------|--------|----------------|---------------------|
| CO₂ | 612 ppm | ▇▇▁▁▁▁ | ▁▂▁▃▂▁ |
| CO | 1.24 Rs/R0 | ▨▨▨▨▨▨ | ▁▁▂▁▁▁ |
| H₂S | 0.88 Rs/R0 | ▨▨▨▨▨▨ | ▁▁▁▁▂▁ |
| 온도 | 24.5 ℃ | ▨▨▨▨▨▨ | ▂▂▃▂▂▂ |
| 습도 | 61 % | ▨▨▨▨▨▨ | ▃▃▃▄▃▃ |
| 가스저항 | 42.1 kΩ | ▨▨▨▨▨▨ | ▅▅▄▅▅▅ |

- **스파크라인은 Recharts 를 쓰지 않고 인라인 SVG `<polyline>` 으로 그린다.** 노드 4개 ×
  지표 6종 = 24개의 미니 차트가 실시간 스트림마다 갱신된다. 각각이 ResponsiveContainer 를
  들고 있으면 리렌더 비용을 감당할 수 없고, 여기서 필요한 건 축도 툴팁도 아닌 선 하나다.
- **근접도 바는 세 상태를 구분한다.** ①서버 임계값 대비 채워진 바 ②판정 불가(임계값
  미수신 또는 규칙 없는 지표) ③미교정(값이 ppm 이 아니라 Rs/R0 이라 비교 자체가 불성립).
  ②·③은 빗금(`▨`)으로 그린다 — 빈 바로 두면 모르는 상태가 "여유 있음"으로 보인다.
  임의의 Rs/R0 만점 눈금을 만드는 것은 임계값 하드코딩이므로 하지 않는다 (FR-201).
- 데이터 버퍼: `sensor_trend: Record<NodeId, Partial<Record<TrendMetric, TrendPoint[]>>>`
  (§10.1). 노드×지표마다 시간 창과 점 수 상한을 둔다.
- Zustand selector 는 **칸 단위로 쪼개 구독한다** (§10.3). 한 노드의 갱신이 나머지 3칸을
  리렌더시키면 안 된다.
- 오프라인 노드 칸: 마지막 값을 흐리게 남기고 `OFFLINE · 마지막 수신 HH:MM:SS` 를 표시한다.
  **값을 지우거나 0으로 만들지 않는다** — 마지막으로 관측된 상태가 남아 있어야 언제부터
  모르는지를 판단할 수 있다.

**2×2 배치 순서 — ①과 일치시킬 것.**

`plan` 카메라 화면에서 **화면 오른쪽 = `x_ship` 감소, 화면 위쪽 = `y_ship` 감소** 다
(05_DIGITAL_TWIN_SPEC §3.1.2.1). 지도처럼 "x 가 오른쪽"으로 착각하기 쉬우나 반대다.

```
   S2 ────── S1      ← 화면 위쪽 (port, 카메라에서 먼 쪽)
   │          │
   S4 ────── S3      ← 화면 아래쪽 (starboard, 절개된 벽 쪽)
```

⑤의 2×2도 같은 순서로 둔다. ①에서 좌상단이 뜨거우면 ⑤의 좌상단 칸을 보면 되도록.
순서는 컴포넌트에 하드코딩하지 않고 `utils/coordinates.ts` 의 `SENSOR_SCREEN_ORDER` 가
단일 소스이며, `coordinates.test.ts` 가 실제 Three.js 카메라 투영과 대조해 검증한다.
좌표나 카메라 각도를 바꾸면 그 테스트가 먼저 깨진다.

### 3.7 ④ 최근 위험 로그

- 데이터: `services/api.ts` 의 `fetchAlertEvents({ limit: 20 })`, 30초 주기 갱신
- 필터: **`level2_warning` 이상만.** L1까지 넣으면 평상시 잡음이 실제 위험 이력을 밀어낸다 —
  고정 높이 칸이라 밀려난 행은 사실상 없는 것과 같다.
- 행 구성: `시각 | 노드 | 유형(한국어) | 등급 배지 | 상태(active/resolved)`
  - 유형 한국어 매핑은 §6.3의 표를 쓴다. 구현은 `utils/alertLabels.ts` 가 단일 소스이고
    Screen 4 이벤트 로그도 같은 표를 본다 — 화면마다 따로 들고 있으면 유형이 하나 늘 때
    한쪽만 갱신되어 같은 사건이 다르게 보인다.
- 시간 역순, 고정 높이 180px 내부 스크롤
- 행 클릭 → 이벤트 로그 화면(Screen 4)으로 해당 노드·등급 필터를 걸고 이동
- 비어 있을 때: `최근 위험 이력 없음` — 빈 표가 아니라 명시적 문구. 표만 비어 있으면
  "로딩 중"과 구분되지 않는다.
- `worker_name` 이 있으면 함께 표시 (경보 **시점**의 착용 작업자, 이슈 #136)

## 10. Zustand Store 구조

### 10.1 전체 구조

```typescript
interface DashboardStore {
  // WebSocket 연결 상태
  ws: {
    connection_status: "connected" | "reconnecting" | "disconnected";
    last_snapshot_at: string | null;
  };

  // Space 객체
  space: {
    dimensions: { width_m: number; depth_m: number; height_m: number };
    overall_risk_level: AlertLevel;
  };

  // 센서 노드 (ID 기반 맵)
  sensor_nodes: Record<string, {
    object_id: string;
    physical_id: string;
    position: { x_m: number; y_m: number; z_m: number };
    position_coordinate_system: "model-local";
    latest_values: Record<string, number | null>;
    alert_level: AlertLevel;
    connection_status: "online" | "offline";
    calibration_status: "uncalibrated" | "calibrating" | "calibrated";
  }>;

  // 웨어러블
  wearable: {
    object_id: string;
    physical_id: string;
    position: { x_m: number; y_m: number; z_m: number };
    position_coordinate_system: "model-local";
    location_quality: {
      quality_score: number;
      anchor_count: number;
      is_filtered: boolean;
    };
    o2_pct: number;
    fall_detected: boolean;
    battery_pct: number;
  };

  // 활성 경보 (alert_key 기반 맵)
  active_alerts: Record<string, {
    alert_id: string;
    source_node_id: string;
    alert_key: string;
    alert_type: string;
    level: AlertLevel;
    message: string;
    status: "active" | "resolved";
    activated_at: string;
  }>;

  // 위험 구역
  hazard_zones: Array<{
    object_id: string;
    source_node_id: string;
    geometry: {
      type: "circle";
      center: { x_m: number; y_m: number };
      radius_m: number;
    };
    trigger_level: AlertLevel;
    active: boolean;
  }>;

  // 노드 × 지표별 추세 링 버퍼 (§3.6 ⑤ 스파크라인, §8.2 선제 표시)
  //
  // CO₂ 전용이던 co2_trend 를 6종으로 일반화한 것이다. O₂ 는 센서 노드가 아니라
  // 웨어러블 값이라 제외한다 (TrendMetric = MetricKey 에서 o2_pct 를 뺀 것).
  //
  // 노드 단위로 객체를 새로 만든다 — 한 노드의 갱신이 다른 노드를 구독하는
  // 셀렉터의 참조를 건드리지 않아야 §10.3 의 칸 단위 격리가 성립한다.
  sensor_trend: Record<string, Partial<Record<TrendMetric, Array<{ t: number; v: number }>>>>;
}
```

**버퍼 상한** — 시간 창만으로는 부족하다. 노드 5 × 지표 6 = 최대 30개 버퍼가 동시에
자라고, 샘플 주기가 빨라지면 창 안에서도 수천 점이 쌓인다. 쓰기 시점에 둘 다 자른다.

| 상수 | 값 | 용도 |
|------|-----|------|
| `SENSOR_TREND_WINDOW_MS` | 60분 | 버퍼가 보관하는 시간 창 |
| `SENSOR_TREND_MAX_POINTS` | 360 | 버퍼당 점 수 상한 |
| `SPARKLINE_WINDOW_MS` | 5분 | ⑤ 스파크라인이 **그리는** 구간 (버퍼는 더 길게 갖고 표시만 잘라 쓴다) |

### 10.2 상태 갱신 규칙

| 메시지 | 갱신 대상 | 방식 |
|--------|----------|------|
| Snapshot | 전체 Store | 전체 교체 |
| Delta (센서 값) | `sensor_nodes[id].latest_values` | 부분 갱신 (revision 확인) |
| Delta (경보 레벨) | `sensor_nodes[id].alert_level` | 부분 갱신 |
| Alert event (active) | `active_alerts[alert_key]` | 추가/갱신 |
| Alert state (resolved) | `active_alerts[alert_key]` | 제거 또는 status 변경 |
| Connection state | `sensor_nodes[id].connection_status` | 갱신 |
| Wearable position | `wearable.position` | 갱신 (좌표 변환 적용) |

### 10.3 렌더링 영역 격리

Recharts(2D 차트) 컴포넌트와 React Three Fiber(3D 캔버스) 컴포넌트는 Zustand selector를 통해 각각 필요한 상태만 구독한다. 대용량 스트림 유입 시 한쪽의 리렌더가 다른쪽에 영향을 주지 않도록 구독을 분리한다.

```typescript
// 2D 차트: sensor_nodes의 특정 값만 구독
const co2Value = useStore((s) => s.sensor_nodes["sensor-01"]?.latest_values.co2_ppm);

// 3D 캔버스: position만 구독
const workerPos = useStore((s) => s.wearable.position);

// Screen 1 ⑤: 칸(노드) 단위로 구독한다. 한 노드의 갱신이 나머지 3칸을 리렌더시키지 않는다.
const node = useDashboardStore((s) => s.sensor_nodes[nodeId]);
const trends = useDashboardStore((s) => s.sensor_trend[nodeId]);
```

> **셀렉터에서 새 객체·배열을 만들지 않는다.** `useSyncExternalStore` 는 스냅숏을
> 참조로 비교하므로, 셀렉터가 매번 새 배열을 반환하면 "스냅숏이 계속 바뀐다"고 보고
> 무한 루프에 빠진다(`Maximum update depth exceeded`). 스토어에 있는 객체를 그대로
> 구독하고 파생(`filter` / `map`)은 렌더 안에서 `useMemo` 로 한다.
>
> ```typescript
> // ✗ 매 호출마다 새 배열 → 무한 루프
> const active = useStore((s) => Object.values(s.active_alerts).filter(a => a.status === "active"));
>
> // ✓ 맵을 그대로 구독하고 파생은 렌더에서
> const alertMap = useStore((s) => s.active_alerts);
> const active = useMemo(() => Object.values(alertMap).filter(a => a.status === "active"), [alertMap]);
> ```

## 11. 시뮬레이션 데이터 표시

`source_mode: "simulation"` 데이터와 실제 센서 데이터를 시각적으로 구분한다.

| 요소 | 실제 데이터 (live) | 시뮬레이션 (simulation) |
|------|-------------------|----------------------|
| 센서 카드 테두리 | 실선 | 점선 |
| 3D 마커 테두리 | 실선 | 점선 |
| 카드 라벨 | 없음 | "SIM" 배지 (회색) |
| 차트 라인 | 실선 | 파선 (dashed) |
| 이벤트 로그 | 일반 표시 | "SIM" 태그 추가 |

> 시뮬레이션 데이터는 실제 센서와 동일한 node_id를 사용하므로, `source_mode` 필드로만 구분한다. (`04_DATA_CONTRACT.md` 섹션 2 참조)
>
> 좌표 비율 매핑은 시뮬레이션 여부와 별개이다. 예를 들어 실제 UWB 측정값도 축소 데모
> 공간에서 측정되어 선박형 트윈에 투영되면 `LIVE` 배지와 `demo-local -> ship-visual`
> 배지를 함께 표시한다.

## 12. 반응형 디자인

| 브레이크포인트 | Screen 1 레이아웃 | 세로 스크롤 |
|---------------|------------------|------------|
| >= 1280px (Desktop) | SideNav + 5분할 2열 (좌 68% / 우 32%), ⑤ 는 2×2 | **없음** |
| 768~1279px (Tablet) | SideNav(아이콘만) + 1열 스택 (① ⑤ ② ③ ④), ⑤ 는 2×2 | 허용 |
| < 768px (Mobile) | 하단 탭바 + 1열 스택, ⑤ 는 1열 | 허용 |

- 1280px 미만에서 우측 컬럼이 좌측 아래로 내려간다. 좁은 폭에서 68/32 를 유지하면 두 열
  모두 판독 불가가 되므로, **그때만** 스크롤을 허용한다.
- 스택 모드에서는 칸이 내용만큼 늘어난다. 페이지가 스크롤되는데 칸마다 내부 스크롤까지
  만들면 스크롤 컨테이너가 이중으로 겹쳐 조작이 엉킨다. ④ 만 예외로 220px 고정이다 —
  이력 20건이 스택 전체를 밀어내면 안 된다.
- 세로가 짧은 관제 모니터(`max-height: 860px`)에서는 여백을 먼저 줄이고, 그래도 모자라면
  ④ 를 150px 로 줄인다. 최근 이력은 현재 상태보다 나중에 봐도 되는 정보다.

> MVP의 주요 타겟은 Desktop (관리자 모니터)이다. Mobile은 SHOULD 수준이다.
